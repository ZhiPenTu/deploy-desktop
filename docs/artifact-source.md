# 制品源与交付包

「制品中心」用于从流水线或直链获取交付包，校验后作为部署向导的输入。交付包由目标项目自行产出，桌面端只按 `bundle.json` 的声明执行，不内置任何项目的目录名称或产物映射。

## 交付包构成

交付包是单个 `.tgz` 压缩包，解包后根目录必须有 `bundle.json`，其余内容全部由声明描述。推荐沿用 `app/`（应用产物）与 `deploy/`（部署配置）两层目录，但这不是硬性要求，产物来源可以是包内任意相对路径。

仓库内的 [bundle.v2.json](../examples/bundle.v2.json) 是一份可直接对照的示例。
示例中的文件大小与摘要为占位值，只用于说明结构；真实交付包必须写入实际值。

### bundle.json v2

`apiVersion` 必须精确等于 `deploy.desktop/bundle/v2`，`kind` 必须为 `DeploymentBundle`。所有对象都拒绝未知字段，拼写错误会直接失败而不是被静默忽略。

| 字段 | 说明 |
| --- | --- |
| `metadata.product` | 产品标识，必填。项目首次绑定交付包时记录，之后不一致会阻止部署 |
| `metadata.displayName` | 界面显示名称 |
| `metadata.version` | 版本号，必填，最多 128 个字符，需与制品源填写的版本一致 |
| `metadata.buildNumber` / `commit` / `commitShort` / `branch` / `builtAt` | 构建信息，用于展示 |
| `metadata.minToolVersion` | 最低客户端版本；高于当前应用版本时阻止使用并提示升级 |
| `runtime.type` | 目前只支持 `compose`，其他取值直接报不支持 |
| `runtime.compose` | 包内 Compose 清单路径，其所在目录即 `deploy` 根 |
| `runtime.variant` | 可选的变体清单，例如局域网覆盖文件 |
| `runtime.containerPrefix` | 容器名前缀；服务未声明 `container` 时为 `<prefix>-<serviceKey>` |
| `runtime.services[]` | `key`、`label`、`port`、`protocol`、`description`、`container`，供监控、日志、环境检查与数据库页使用 |
| `runtime.database` | `serviceKey`、`name`、`client`、`port`；`serviceKey` 必须存在于 `services` |
| `artifacts[]` | `key`、`label`、`source`、`root`、`path`、`type` |
| `components[]` | `key`、`label`、`artifacts[]`、`services[]`，部署向导据此提供组件选项 |
| `images[]` | `name`、`ref`、`role`、`required`、`bundleFile` |
| `plan.steps[]` | `key`、`title`、`hint`，为部署向导的步骤补充说明 |
| `files[]` | `path`、`size`、`sha256`，必须覆盖包内除 `bundle.json` 外的全部文件 |

`artifacts[].root` 只接受 `install` 或 `deploy`，`type` 只接受 `file` 或 `dir`。`images[].role` 为 `app`（应用镜像）或 `base`（基础镜像）；声明 `bundleFile` 表示镜像以 `docker save` 包的形式随交付包分发，未声明则由目标机自行准备。

### 目标路径

- `install` 根是项目配置的部署目录，`deploy` 根是 `runtime.compose` 所在目录。
- `path` 相对对应的根解析，`source` 相对交付包根解析。
- 两者都必须是相对路径：绝对路径、`..`、反斜杠和符号链接一律拒绝；规范化后必须仍在对应根内。
- 同一根下的同一路径只能声明一次；`runtime.compose` 自身必须被某个产物声明为 `source`。

例如把接口程序放到部署目录的 `services/api/`、把网页产物放到 `deploy/site`：

```json
{
  "key": "server-jar",
  "label": "后端程序",
  "source": "app/api.jar",
  "root": "install",
  "path": "services/api/api.jar",
  "type": "file"
}
```

目标机上 Compose 的挂载路径需要与这里一致，例如清单位于 `deploy/` 时用 `../services/api/api.jar` 就能命中同一个文件。桌面端不做路径猜测，挂载位置与实际写入位置不一致会在增量更新的挂载检查中被拦下。

### 校验规则

打开交付包时执行结构校验：`apiVersion` 与 `kind`、必填字段、产物与组件的唯一性、组件引用的产物与服务是否存在、每个文件是否归属某个产物或镜像包、Compose 清单是否已声明、`minToolVersion` 是否满足。

解包完成后逐条比对 `files[]` 的 `size` 与 `sha256`：包内出现未声明的文件、缺少声明的文件或摘要不符都会拒绝，`.DS_Store` 会被忽略。

旧版交付包（含 `schemaVersion`、`mode`、字符串数组形式的 `components`）不再兼容，桌面端会提示使用新版流水线重新构建。

## 目录位置

| 平台 | 应用配置目录 |
| --- | --- |
| macOS | `~/Library/Application Support/com.deploydesktop.app` |
| Windows | `%APPDATA%\com.deploydesktop.app` |
| Linux | `~/.config/com.deploydesktop.app` |

- `projects.json`：项目列表与当前项目，见[部署配置与主机管理](configuration.md)。
- `artifact-sources.json`：制品源列表。
- `artifact-releases-cache.json`：最近一次成功获取的版本列表，供离线时先展示；不保存下载地址。
- `bundles/<sourceId>/<version>/`：解包后的交付包。

在制品中心「设为当前部署包」会把该目录绑定到当前项目，部署向导、监控与日志随即使用这个交付包声明的拓扑。

## 制品源类型

### 云效流水线

填写组织 ID、流水线 ID、制品名与个人访问令牌。桌面端会：

1. 分页请求运行列表，筛选 `SUCCESS` 记录。
2. 请求运行详情，按制品名匹配上传结果，兼容 `.tgz` / `.tar.gz` 后缀。
3. 读取 `downloadUrl`、`md5`、`version`、`fileSize`；版本为必填字段，兼容字符串和数字类型的历史构建号。
4. 下载并按上述规则校验、解包。

配置文件 `artifact-sources.json` 记录组织、流水线、制品名与版本信息，不保存令牌。当前令牌由本机凭据文件单独管理，Unix 权限为 `0600`，旧钥匙串凭据会迁移到当前存储。

### 直接下载地址

适用于自建制品服务器、对象存储或内网文件服务。需填写制品名、版本号和下载地址，版本号必须与 `bundle.json.version` 完全一致。版本号以字母或数字开头，只接受字母、数字、点、短横线和下划线，最多 128 个字符。地址在保存时写入本地配置，下载时只接受与该配置完全一致的 URL，不接受前端临时传入的其他地址。

旧配置未填写版本号时，可沿用最近下载且已标注的版本。若没有有效版本，请在「设置」的「制品设置」中补充；不再使用 `manual` 作为可下载版本。修改下载地址时应同时更新版本号，本地旧版本不会被误标为新版本的缓存。

仅允许 `https://` 下载。云效流水线来源额外限制下载域名必须是 `aliyuncs.com` / `aliyun.com` 及其子域，避免恶意地址被用来读取任意主机内容。下载体积上限为 5 GiB。

## 按制品源查看

制品中心先列出已配置的制品源，点击名称或「查看制品」进入该来源的制品列表，也可在列表上方切换来源。新增、编辑与删除在「设置」的「制品设置」中完成。每行显示制品名、版本号、构建信息、大小与本地状态，支持下载、使用已下载包和查看运行详情。

打开某个来源时，页面先读取本机缓存：上次成功获取的版本列表，以及 `bundles/<sourceId>/` 中已下载的交付包，随后再请求云端最新版本。网络不可用时保留缓存内容并提示连接失败，不会把列表清空；缓存中没有下载地址的版本只能使用已下载的交付包，连接恢复后刷新即可重新下载。

最新制品按构建时间倒序排列，不按版本号字典序排序。可加载更早的构建记录；当前页没有成功构建时仍可继续加载历史记录。只有名称匹配的上传结果才属于该源，不会回退到其他制品。

下载完成后桌面端会依次校验：源提供的 MD5、压缩包路径安全（绝对路径、`..`、符号链接）、包结构与描述符、包内版本与所选版本是否一致。先在临时目录解包，全部校验通过后再替换该版本的本地缓存；校验失败不覆盖已有交付包。

## 交付包链路

选定交付包后，制品中心展示「交付包链路」：获取交付包 → 准备基础镜像 → 分发交付包 → 启动容器栈 → 验证与验收。步骤来自 `plan.steps`，每一步标注就绪 / 按需 / 待补齐；链路下面是各组件产物从包内路径到目标路径的映射、镜像清单以及目标机的镜像状态。

镜像分两类：

- 随包镜像：`images[]` 中声明了 `bundleFile` 的条目，部署时导入目标机，缺一个就无法启动。
- 基础镜像：`role` 为 `base` 的条目，由 Compose 的 `image:` 行引用，只在首次部署前准备一次。

首次部署还需要一个离线介质目录，自行放置：

```text
<mediaDir>/
  images/               docker save 生成的镜像 tar
  docker-engine/        Docker 离线安装包
```

## 部署向导

部署向导按以下顺序执行，主机与部署目录来自当前项目，不再单独选择本地或远程模式：

1. **选择主机**：显示当前项目绑定的主机与部署目录，可在此确认目标路径；需要更换目标时请切换项目。
2. **检测环境**：检查目标主机的系统资源、Docker、Compose，以及 `runtime.services` 声明的端口。Docker 或 Compose 未就绪时不能继续。
3. **选择制品**：选择制品源的最新版本、已下载包、本地 `.tgz` / `.tar.gz`，或已解压目录。此时只选择候选，不改变当前部署包。
4. **解压制品**：下载或解压所选制品，检查路径安全、结构与文件摘要。压缩包解压到应用配置目录下独立的 `bundles/local/` 子目录，不覆盖原文件；已解压目录直接检查。检查通过后把交付包绑定到当前项目，并核对 `metadata.product` 与项目记录的产品是否一致。
5. **清单比对**：读取包内 `runtime.compose`（存在 `variant` 时一并读取），与目标机现有清单对比服务新增、变化、移除情况，并按完整镜像引用检查目标 Docker。离线镜像包存在不等于镜像已导入；缺失或未确认的镜像会阻止进入执行步骤。可在本步骤选择本机离线介质目录，上传（远程主机）并导入后重新比对。
6. **选择更新**：空部署目录可以首次部署；已有 Compose 的目录只开放增量更新。组件选项来自 `components[]`。执行前重新预检，再确认主机、目录、版本与影响范围。

首次部署会分发交付包、启动 Compose，并检查容器运行状态。数据库迁移由应用启动时处理，向导不自动导入全量 SQL，避免覆盖已有业务数据。部署成功后在部署目录写入 `.deploy-desktop/deployed.json`，记录版本与已写入的产物；写入失败只影响状态展示，不改变部署结果。

增量更新通过 SSH 或本机专用更新命令执行；本机更新要求 Docker 连接指向本机，并核实所选组件对应的服务确实挂载了目标路径。目标 Compose 所在目录由 `runtime.compose` 决定，比对、预检与执行使用同一目录。预检不替换文件、不创建备份、不重启服务；执行时才备份并替换所选内容。本机更新不删除数据卷，不隐式拉取镜像或构建镜像。

服务命令完成后仍会核对实际容器状态。未运行或健康检查尚未通过时显示待确认，不显示部署成功。浏览器预览不能执行向导，也不能作为真实部署结果。

### 比对边界

- 服务差异按 Compose 声明比较，不把服务移除自动解释成删除容器、数据或卷。
- 环境变量、端口和其他配置差异只作为确认信息，不要求新旧配置完全相同。只有勾选「部署配置」才替换配置文件；未勾选时，本机预检使用当前配置，不因制品中未采用的项目名称、环境变量等变化阻止产物更新。更新配置时仍校验 Compose 项目身份，更新产物时仍校验实际挂载位置，镜像、路径和容器归属检查保持有效。
- 清单比对中的「查看配置对比」和服务变化入口展示本次核对读取的完整 Compose 文件快照，左侧为旧版（当前部署），右侧为新版（所选制品）。按行对齐，旧版删除或修改标红，新版新增或修改标绿，支持同步滚动及差异跳转；服务入口定位到对应服务。完整文件包含顶层配置和注释，文本差异可能多于服务声明差异。展示时隐藏敏感值，但仍按原始内容判定变更；仅用于查看，不改写配置文件。
- 镜像按完整引用核实，包含 `@sha256:` 时不回退为 tag。尚含 `${...}` 的镜像地址视为未确定，需补齐制品后重试。
- 远程状态优先读取 `.deploy-desktop/deployed.json` 逐个探活已写入的产物；记录缺失时只显示容器状态，不推测产物信息。
- 本地目录的检查覆盖路径安全和结构；本地压缩包无上游摘要时不声称完成来源完整性验证。云端下载仍按制品源提供的 MD5 检查。
- 操作进行时暂不能切换项目或页面，执行参数同时使用独立快照，避免任务途中切换目标。

## 在流水线侧产出

在目标项目的流水线中构建应用产物与部署配置，按上面的规则生成 `bundle.json` 后上传为单个制品。本仓库不含目标项目的流水线配置，`tt_net_manager` 的做法可以参考：

- `deploy/bundle.config.json` 保存产品、运行时、服务、数据库、组件、产物、镜像与部署步骤；
- 脚本据此展开产物来源、计算 `files[]` 摘要、校验 Compose 的 `image:` 行与 `images[]` 一致，再写出 `bundle.json`；
- 交付包的 `version` 与流水线上传的制品版本必须一致，推荐 `${BUILD_NUMBER}-${CI_COMMIT_ID}`，例如 `8-a1b2c3d`。缺少构建号或提交号时直接让打包失败，不能回退到 `dev` 或空值；
- 包内只保留已声明的内容。未声明的文件不参与分发，桌面端也会把多余文件判为校验失败。
