# 部署执行与扩展

部署更新分为三层，业务编排不直接管理子进程或拼接带数据的 Shell 语句。

| 层 | 桌面 | MCP | 职责 |
| --- | --- | --- | --- |
| 进程执行 | `core/process.rs` | `src/exec.mjs` | 输入、并行读取输出、退出状态、超时、输出上限与进程清理 |
| Bash 与传输 | `core/shell.rs`、`remote_ssh/client.rs`、`remote_update/transfer.rs` | `src/shell.mjs`、`src/ssh.mjs` | 参数绑定、SSH 传输及暂存生命周期 |
| 部署编排 | `remote_update/update.rs`、`local_update.rs` | `src/update.mjs` | 包校验、备份、产物替换、应用配置和服务就绪 |

这里的 Rust 路径相对 `src-tauri/src/`，MCP 路径相对 `mcp-server/`。首次分发与镜像上传复用相同的远程文件替换能力，本机更新的 Docker / Compose 命令也使用统一进程执行器。构建同步入口通过 Bash 文件执行封装运行既有脚本。

## Bash 模板

两端共用根目录 `shell/`：

- `transfer.sh`：准备暂存、接收文件或压缩流、提交替换、清理。
- `backup.sh`：按安装根的相对目录保存备份，避免安装根与部署根下的同名路径冲突。
- `compose-update.sh`：按清单路径应用配置与重启服务，使用参数数组。
- `readiness.sh`：通过 Compose 获取实际容器 ID，再检查运行与健康状态。

更新、备份、替换模板统一启用 `set -euo pipefail`。参数通过 `set --` 绑定为位置参数，所有值使用单引号转义；NUL 被拒绝。禁止把路径、服务名或描述符字段插入命令语法、双引号消息或 `eval`。数组保持参数边界，命令接受时用 `--` 结束选项。

普通脚本通过 SSH 的标准输入发送；完整脚本放在复合命令中，让 Bash 先解析完再执行，避免内部读输入的命令吞掉后续脚本。二进制传输保留标准输入给文件数据，仅把不含凭据的传输程序通过 `bash -c` 传递。现存只读探测脚本不统一强加严格模式，以保留其显式容错行为。

模板不能依赖本机工作目录。Rust 通过 `include_str!` 嵌入，MCP 相对模块 URL 读取；复制或打包 MCP 时须携带 `shell/`。模板兼容 macOS Bash 3.2 与 Linux Bash，不依赖目标机安装 Node.js 或 Python。

## 文件替换和失败边界

1. 在目标同级通过 `mktemp -d` 创建本次任务独占的暂存目录。
2. 文件写入暂存内容；目录由本机 tar 产生压缩流，目标机只解包到暂存目录。
3. 本机生产者、SSH 接收端均成功后，才发起独立的提交操作。即使 tar 产生了可解包的部分归档，只要最终退出非零，就不提交。
4. 提交时用目标同级目录锁避免同时替换同一路径。旧目标改名到暂存目录的 `previous`，然后让新内容落位。
5. 落位失败尝试恢复旧目标。恢复失败时保留 `previous` 并报告位置；清理程序拒绝删除恢复副本或仍被替换锁保护的暂存目录。
6. 新内容落位后清理旧目录失败不改变更新结果，只记录日志并在服务重启后再次尝试；旧文件仍在时保留临时目录，避免把已完成替换误报为失败。
7. 本机 Windows 更新遇到文件占用或共享冲突时，先停止所选组件中实际挂载这些文件且正在运行的服务释放句柄，再短暂等待并重试替换；仍失败时保留停止状态并在错误中说明，避免把新旧文件混合后启动。同一路径还被未选中的运行服务挂载时，更新会在替换前阻止并提示先停止该服务。

备份目录带随机后缀，不再只依赖秒级时间戳。备份验证全部路径后才创建目录，并保留完整安装根层级。

这些保证适用于单个产物；多个产物的更新与 Docker 操作不是一个整体事务。前面成功写入的组件不会在后续组件或就绪检查失败时自动回滚。失败结果保留备份目录和已完成步骤，供用户检查恢复。锁仅保护单次路径替换，不负责串行化整个部署流程。

进程被强制结束或网络断开后，不能推断远端操作已经取消。目标状态不明时返回失败，不自动重试写操作。遇到残留锁应先核实没有正在执行的部署，再检查暂存目录和恢复副本；不要仅按锁的年龄自动删除。

## 执行限制与结果

- 默认单进程执行上限 10 分钟，上传和备份 30 分钟，构建同步脚本 60 分钟；调用者可明确指定更合适的上限。
- 标准输出与错误输出分别最多保留 4 MiB，超过后仍持续读取以防阻塞。需要解析完整结果的调用拒绝把截断结果当成成功。
- 输入、标准输出、错误输出和等待退出同时进行，避免大文件或大量错误输出填满管道。
- 超时覆盖传输与等待过程。Unix 终止本机进程组；Windows 终止直接子进程，关闭管道。不能据此保证远端命令已经停止。
- 生产者失败、输入流失败、非零退出和超时都不能触发后续提交。MCP 即使收到零退出码，只要已触发超时也按失败处理。
- 本机原生命令使用 argv，不经过 Bash。不要把进程参数或完整脚本加入日志；其中可能包含敏感配置。

应用配置使用 `up -d --pull never --no-build --remove-orphans`，重启列表和等待列表来自交付包。就绪必须满足容器正在运行，且健康状态为 `healthy` 或没有健康检查；失去运行状态但仍残留 `healthy` 不能通过。缺失服务立即失败。镜像分发与导入仍受各入口既有预检和确认约束。

## 清单比对中的镜像准备

清单比对会逐项返回镜像状态：`ready`、`missing`、`platform_mismatch`、`check_failed`、`unavailable` 或 `invalid`。平台不匹配时会同时返回现有镜像平台与目标平台，不再把“架构不一致”笼统显示为“未确认”。标签镜像与带 `sha256` 摘要的镜像都可以按目标架构重新拉取（`docker pull --platform`）；若仓库中的该摘要不含目标架构，Docker 会提示找不到匹配版本，这时需要更换交付包。

按摘要固定的镜像无法通过镜像包保留原仓库引用：`docker load` 只登记标签，不会重新登记 `仓库@sha256:...` 引用。为此，“本机拉取后传入”会在源端记录该镜像的内容标识（镜像 ID），传到目标机后按内容标识逐个核对，并把核对结果写入目标部署目录的 `.deploy-desktop/image-bindings.json`；目标机上的镜像核对会按这份记录确认镜像存在，部署时用一份按内容标识生成的 Compose 覆盖文件替换对应的 `image` 字段并禁止拉取，因此目标机无需访问镜像仓库也能使用按摘要固定的镜像。“离线镜像包”无法核对包内内容与仓库摘要，因此不会传输这类镜像，界面会提示选择“本机拉取后传入”或由目标主机直接拉取。

准备镜像提供三种来源：

- **从镜像仓库拉取**：本机目标调用本机 Docker，远程目标通过既有 SSH 连接在目标机执行。前端按镜像仓库分组列出可用的已保存镜像源，公开镜像可以留空使用现有登录状态，私有镜像可为每个仓库分别选择镜像源并填写本次凭据。`pull_deployment_images` 先验证所选引用确实来自交付包，再按引用所属仓库匹配凭据；未选择源时使用目标机已有 Docker 登录状态。本机直连 Docker Hub 失败且未选择凭据时，会按顺序尝试仍保留的预置公共加速源；Docker Hub 可达时核对两边清单摘要，不可达时以加速源清单内容计算摘要并按摘要拉取，拉取后核对平台再保存为交付包中的原镜像地址。检测到 Docker Hub 登录凭据、摘要引用和校验不一致的情况不会自动回退。使用临时 Docker 配置时会保留当前 context、`contexts/` 与 `certs.d/`，避免把镜像拉到另一个 Docker 实例。远程发送已保存凭据前还要求目标主机已记录在 `known_hosts`，未记录时不会传输密码。
- **本机拉取后传入**：用于目标机处于局域网、无法访问镜像仓库的场景。`prepare_local_deployment_images` 先读取目标 Docker 平台，在本机执行 `docker pull --platform <目标平台>`；已经存在且平台一致的镜像会直接复用。随后按既有导出、上传、导入流程把镜像包传入目标机，目标机只负责加载镜像。目标机不需要访问镜像仓库。
- **离线镜像包**：选择本机离线镜像包目录，只传输待处理镜像对应的镜像包，随后在目标机解压并导入。

所有方式都不重启服务，完成后按清单中的完整引用重新检查镜像平台。`docker pull` 需要调用 Docker 凭据助手；应用会为 Docker 命令子进程补全 Docker 桌面版、OrbStack、用户目录与系统目录的 PATH，避免 GUI 进程继承的 PATH 找不到 `docker-credential-*`。

离线方式通过重新核对的 `localFile` 匹配所需镜像包，同一包只上传一次，不上传目录中的无关文件。远程镜像包保存在安装根目录下本次任务独占的 `bundle-images-<任务标识>/images/`，上传成功后由 Docker 加载，支持 `.tar`、`.tgz`、`.tar.gz`，无需单独解包到服务目录。上传采用临时文件加原子替换，只有远端文件的大小与 SHA-256 都与本地一致时才跳过上传。镜像包保留供后续检查，导入不重启服务。

确认前冻结主机、凭证、目录和待处理镜像列表，执行期间阻止重复操作和页面切换。拉取、导出、上传、导入和重新核对分别展示状态，任一步失败均不显示成功。最终仍按清单中的完整引用（含 digest）重新检查 Docker；归档中的标签或摘要不能满足清单要求时保持缺失或不匹配状态，不用标签替换 digest，也不放开部署按钮。

清单比对同时读取交付包声明的制品文件，并按交付包记录的 SHA-256 摘要核对目标文件内容，界面显示已存在、缺失、不完整、路径异常或待写入状态。首次部署的制品显示为“待写入”，已有部署缺少文件时会提示下一步增量更新将写入所选组件，并提供“下一步：选择并写入制品”直接进入该步骤。路径类型不符、包含符号链接或无法读取的文件会阻止继续，处理后重新检查即可。

项目环境变量保存在应用配置目录的 `project-envs/<项目标识>.env`，Unix 权限为 0600，内容不写入运行日志。本机首次部署和增量更新会在执行 Compose 前写入部署目录的 `.env`；远程首次部署和增量更新通过 SSH 以临时文件加原子替换上传到目标部署目录的 `.env`，上传脚本使用 `umask 077`。未配置环境变量的项目不会创建或覆盖目标 `.env`。

## 扩展与验证

新增通用 Shell 操作时先增加静态模板或模板中的受限操作分支，再在两个适配器增加参数绑定；不要新增独立 `spawn`、未受控管道或手写字符串转义。业务特有的组件选择保留在编排层，服务和路径继续来自 `bundle.json`。

至少覆盖成功、特殊字符参数、失败不覆盖原内容和资源清理。涉及管道时增加接收端提前退出、生产者非零退出、大输出与超时测试。涉及替换时增加落位失败与恢复失败用例。

```bash
node --test mcp-server/test/exec.test.mjs mcp-server/test/shell.test.mjs mcp-server/test/ssh.test.mjs
cargo test --manifest-path src-tauri/Cargo.toml core::process
npm run test:mcp
npm --prefix mcp-server run smoke
cargo test --manifest-path src-tauri/Cargo.toml
cargo check --manifest-path src-tauri/Cargo.toml
```

Shell 测试在临时目录运行真实 Bash，用本机传输替身代替 SSH，并模拟 Docker 与故障命令；Windows 跳过 Unix 目标模板测试。它们验证执行协议和故障行为，不代表桌面实机、真实 SSH 或目标环境部署验证。
